# Working on Signal Mission Lab

The repository owner authorizes implementing requested improvements, reviewing and testing them, creating a pull request, and merging it after validation without requesting a separate PR review. Check the current PR head and merge that exact tested revision. Fix failed checks before merging; do not bypass failing checks or claim that a pending test passed. Confirm the merged tree and report the result.

Use public sources for equipment and doctrine. Keep equipment variants, transport, server infrastructure and applications distinct. Explain setup rationale, observable evidence, operational impact, supported users, validated alternatives and recovery acceptance. Mark editorial scenarios and unresolved technical-manual or source gaps honestly. Never invent configurations or claim that a simulator proves equipment readiness or interoperability.

Keep pages readable, with plain labels and large text. Use synthetic training data only. Do not persist mission descriptions, leader-update drafts or credentials. Do not add external messaging, deployment, paid services or identity integrations without an applicable user request.

Validate changes with the source publication gate, relevant Python and Node tests, TypeScript/build and browser journeys. Use the full PR pipeline for database, backup/restore, dependency/security, container and mobile checks. Accessibility checks cover automated rules; they do not replace manual keyboard or assistive-technology review. A clean review means no known actionable defect in the reviewed scope, not a claim that the product has no remaining limitations.
