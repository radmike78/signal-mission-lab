# Review of equipment learning and application quality

Reviewed the current application after PR #7: equipment learning, mission intake, assessment and diagnostic validation, source publication gates, local privacy, instructor learning, offline updates, mobile layout, accessibility and build/CI behavior.

## Fixed

- Mission text now preserves explicit JBC-P, MMC-S, MMC-T, HF and STT+ study selections. STT and STT+ remain distinct; negated selections remain excluded. Bare MMC does not silently pick a software or transport variant.
- Diagnostic evidence-list bounds use catalog checks, independently of assessment question count. Regression checks cover both public and connected submission models and reject oversized lists.
- Equipment mission lessons now have an explicit schema/review state and a publication gate. It checks source origins, duplicate/dangling references, content, exercise stages and worked briefing examples. The gate cannot grant human review.
- Ten fictional leader-update examples distinguish observed facts, possible mission effects, untested alternatives, recovery actions, restoration uncertainty and the next update. The 15-minute interval is an exercise choice, not doctrine.
- Leader-update textareas disable autocomplete/spellcheck; submitted reviews receive keyboard focus. Drafts remain in memory only.
- Equipment lessons load in a separate chunk. The main JS chunk fell from approximately 569 kB to 454 kB (uncompressed), eliminating the previous 500 kB chunk warning. Offline precaching still includes the equipment chunk.
- Automated WCAG A/AA checks now run in CI across all 12 learning areas and expanded desktop/mobile leader-update practice. This supplements existing keyboard/mobile tests, rather than asserting complete accessibility conformance.
- The platform workflow runs on PRs and main pushes, avoiding duplicate full runs on feature branch pushes. Superseded runs on the same ref are cancelled and the job has a 30-minute limit.
- Repository instructions record the owner's implement/review/test/PR/merge workflow without a separate approval step.

## Validation

Local source gate, 42 content tests, 51 Node model tests, 59 backend tests (three PostgreSQL cases require CI infrastructure), production TypeScript/Vite/offline build, browser journeys, connected learning, automated accessibility scan, dependency audits and Python static security checks. GitHub PR checks additionally exercise PostgreSQL authorization and backup/restore, constrained containers and Android/iOS builds. Final CI status is recorded on the PR.

## Remaining limits requiring evidence or external setup

These are visible limitations, not completed work:

- The catalog contains 87 study entries. Seventy still lack a researched failure guide; eight equipment source discoveries are pending. The ten new mission-impact lessons do not make those gaps disappear.
- Applicable public operator/maintainer manuals, exact variants, software baselines and interface documents are needed before equipment-specific configuration instructions or interoperability claims can be validated. Do not replace those with invented steps or infer a universal Army baseline.
- Human technical/doctrine review remains pending. An automated publication gate checks structure and source boundaries, not technical truth or releasability approval.
- Automated accessibility scans and browser keyboard checks do not replace assistive-technology user testing.
- Mobile artifacts are unsigned test builds. Signing, store accounts/submission details and physical-device acceptance remain outside this review. Production identity integration and a verified deployment remain separate work.

No additional reproducible defect was found in the exercised flows after these fixes. This is a scoped review result, not a claim that no future issue or content update is possible.
